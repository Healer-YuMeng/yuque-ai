人工智能教育平台销售咨询 AI
第一版开发实施方案文档
说明：本次只输出方案文档，不进行代码开发、不提交代码、不创建 PR。
目标：基于现有项目，从“语雀知识库问答助手”调整为“访客模式下的销售咨询 AI”，实现主动欢迎、产品答疑、销售引导、联系方式收集、访客模式隐藏参考来源等核心能力。
1. 项目现状判断
1.1 当前项目能力
当前项目已有以下基础能力，可以作为第一版销售咨询 AI 的底座：
FastAPI 后端；
React + TypeScript + Vite 前端；
/chat 与 /chat/stream 聊天接口；
语雀知识库检索；
RAG pipeline；
向量检索与 FAISS；
MCP fallback；
SQLite 问答日志；
前端聊天界面。
README 中明确当前系统是基于语雀知识库的 Enterprise RAG MVP，具备 FastAPI、手写 RAG pipeline、语雀文档拉取、文本切片、embedding、FAISS 检索、MCP fallback、Web 问答页面和 SQLite 日志能力。 
当前 FastAPI 路由已经提供 /chat 和 /chat/stream，可用于非流式和流式问答。 

QAService 当前负责组装 YuqueLoader、VectorStore、DocumentRepository、QALogRepository、Retriever、Generator、MCPClient 和 RAGPipeline，因此第一版可以在此基础上增加销售咨询模式，而不是完全重写。 

1.2 当前方向与新需求差异
当前系统主要是：
用户提问
↓
检索语雀知识库
↓
基于知识库回答
↓
展示来源
新需求需要变为：
访客进入页面
↓
AI 主动欢迎
↓
识别访客大致身份和兴趣
↓
基于语雀知识库回答产品问题
↓
用销售顾问口吻继续引导
↓
识别购买/试用/咨询意向
↓
引导留下电话或微信
↓
访客模式不展示参考来源
因此，RAG 仍然保留，但角色从“主产品形态”变为“销售咨询 AI 的知识工具”。
2. 第一版目标
2.1 产品目标
第一版只做访客模式。
目标是：

让任何对自研人工智能教育平台感兴趣的访客，都可以通过网页聊天了解产品，并在 AI 的自然引导下留下电话或微信，方便后续销售跟进。
2.2 第一版核心功能
第一版需要实现：
访客无需登录即可聊天；
新会话自动出现 AI 欢迎语；
AI 能基于语雀知识库回答产品相关问题；
AI 回答风格从“知识库问答”调整为“真人销售顾问”；
AI 能识别访客身份倾向，例如机构、老师、学生、家长；
AI 能识别购买、试用、演示、咨询等高意向表达；
AI 能自然引导访客留下电话或微信；
电话或微信只需留一个；
访客模式不展示参考来源；
用户长时间无互动时，AI 可温和提示留下联系方式；
暂不做登录、注册、销售模式、付费客户模式、CRM、人工接管。

4. 总体技术方案
4.1 推荐策略
第一版不建议大规模重构。
推荐采用：

在现有 /chat/stream 基础上增加 visitor_sales 模式
原因：
当前后端已有 /chat/stream，可以继续用于流式回复。 
当前 QAService 已经封装了 RAG pipeline。 
当前 RAGPipeline 已经负责检索和生成。 
第一版需求主要是产品形态和 prompt 策略变化，不一定需要立即重写 API。
后续如果要做登录、CRM、多角色，再新增 /conversation API。
4.2 第一版架构
建议第一版逻辑如下：
Frontend Chat UI
  ↓
POST /chat/stream
  ↓
QAService.chat_stream
  ↓
Visitor Sales Router
  ├── 识别联系方式
  ├── 识别购买/试用/演示意向
  ├── 识别访客类型
  └── 判断是否需要 RAG
        ↓
     RAGPipeline
        ↓
  Visitor Sales Generator Prompt
        ↓
返回自然销售型回答
        ↓
Frontend 隐藏 sources
4.3 RAG 的新定位
现有 RAG 继续用于回答：
平台介绍；
功能说明；
使用指南；
案例；
教育场景；
常见问题；
试用或购买说明中已有知识库内容。
当前 RAGPipeline.run 会先检索上下文，再调用 generator 生成回答。这个流程可保留。

5.4 Generator Prompt 改造
当前 DeepSeekGenerator 的系统 prompt 固定要求输出：

## 参考来源
这不适合访客销售咨询。 
建议新增访客模式 generator 或 prompt 分支。

方案 A：新增 VisitorSalesGenerator
优点：
不影响原有 RAG 问答；
后续销售登录模式可以继续用原 generator；
访客 prompt 清晰独立。
建议：
app/rag/generator.py
  DeepSeekGenerator
  OpenAIGenerator
  VisitorSalesGenerator
或者单独新增：
app/conversation/visitor_generator.py
方案 B：在现有 Generator 中增加参数
例如：
generate(question, contexts, sources, style="default")
如果 style == "visitor_sales"，使用访客 prompt。
优点：

改动集中；
复用现有 streaming 逻辑。
缺点：
原 generator 逻辑会变复杂；
后续多角色扩展可能变乱。
推荐
第一版推荐 方案 A 或轻量 A：
新增访客 prompt builder，但复用现有 OpenAI client 调用逻辑。
5.5 访客销售 Prompt 草案
建议系统提示词：
你是一个自研人工智能教育平台的销售咨询顾问。

你的目标：
1. 用自然、亲切、专业的中文接待访客；
2. 基于知识库内容介绍平台功能、使用场景、使用指南和案例；
3. 根据访客身份调整讲解重点，访客可能是学校/机构负责人、老师、学生或家长；
4. 每次回答后，尽量自然引导访客继续了解一个相关问题；
5. 当访客询问购买、试用、演示、价格、合作、开通等内容时，温和引导留下电话或微信；
6. 访客留下电话或微信后，确认收到，并说明后续产品顾问可以进一步沟通；
7. 不要强迫用户购买，不要频繁索要联系方式；
8. 不要输出“参考来源”章节；
9. 不要暴露知识库来源或内部文档；
10. 不要编造知识库没有的信息；
11. 如果知识库没有明确答案，请坦诚说明，并建议留下联系方式由产品顾问进一步确认。

回答风格：
- 像真人销售顾问；
- 简洁、有温度；
- 不要一上来长篇大论；
- 一次只追问一个主要问题；
- 不要使用固定的“## 回答 / ## 参考来源”格式。
5.6 留资识别逻辑
电话识别
第一版规则：
(?<!\d)1[3-9]\d{9}(?!\d)
微信识别
第一版规则不宜过严，可识别：
微信 xxx
微信：xxx
微信是 xxx
我的微信是 xxx
wx xxx
wx: xxx
wechat xxx
wechat: xxx
微信号提取建议先限定：
[a-zA-Z][-_a-zA-Z0-9]{5,19}
但要注意，有些用户微信可能不是标准格式，第一版可以将“微信是”后面的短文本作为候选。

6. 前端设计方案
6.1 当前前端基础
当前前端是 React + TypeScript + Vite，已有聊天应用基础。 
Vite 开发代理已经把 /chat、/mcp、/docs、/yuque 转发到后端。 

App.tsx 中已经存在聊天状态、模型选择、会话状态、MCP 数据、文档选择等状态。 

6.2 第一版前端调整
需要做
页面定位改为销售咨询 AI；
新会话自动插入欢迎语；
输入框提示改为销售咨询场景；
隐藏参考来源；
隐藏或替换现有内部 skill 快捷按钮；
增加访客快捷问题；
增加长时间无互动提醒；
识别用户是否已经留下联系方式；
防止重复留资提醒。
6.3 欢迎语实现方案
推荐前端实现
新会话初始化时，前端直接插入一条 assistant 消息：
您好，欢迎了解我们的人工智能教育平台。
我可以帮您介绍平台功能、适用场景、使用方式和案例。为了更准确地给您推荐内容，我想先了解一下：您是学校或机构负责人、老师、学生，还是家长呢？
原因：
简单；
不消耗 LLM；
体验稳定；
后续可以再改成后端动态欢迎语。
6.4 快捷问题按钮
当前前端已有一些偏内部知识库助手的 skill，例如阅读笔记、碎片整理、润色、知识关联、文档搜索、摘要、过期检测等。
访客模式建议隐藏这些按钮，替换为：

平台是做什么的？
适合老师怎么用？
适合家长了解什么？
有哪些使用案例？
可以申请试用吗？
怎么购买或合作？
6.5 长时间无互动提醒
建议前端实现。
触发规则
访客已发送至少一条消息
且最近 60-90 秒无新消息
且 AI 不在生成中
且用户没有正在输入
且本会话没有提醒过
且未识别到联系方式
插入消息
如果您现在暂时不方便继续了解，也可以先留下电话或微信。我们可以安排产品顾问把平台介绍、使用案例和试用方式发给您，后续您有时间再详细沟通。
6.6 隐藏参考来源
当前回答可能有 sources。第一版访客模式前端需要：
不展示 sources
不展示 source links
不展示 “参考来源”
同时后端 prompt 也要避免生成“参考来源”章节。

9. 人工确认点
在正式开发前，需要你确认以下内容。
9.1 产品范围确认
请确认：
第一版只做访客模式，不做登录、注册、销售模式、付费客户模式。
9.2 欢迎语确认
建议欢迎语：
您好，欢迎了解我们的人工智能教育平台。
我可以帮您介绍平台功能、适用场景、使用方式和案例。为了更准确地给您推荐内容，我想先了解一下：您是学校或机构负责人、老师、学生，还是家长呢？
请确认是否使用这版。
9.3 无互动提醒时间
请确认：
60 秒
90 秒
其他时间
我建议第一版使用 90 秒，避免过早打扰。
9.4 是否保存联系方式
这是最关键的确认点。
方案 A：第一版不保存
优点：
开发更快；
不涉及数据表。
缺点：
留资业务闭环弱；
页面刷新后信息丢失；
AI 不能说“已记录”。
话术应使用：
收到，后续可以根据您留下的联系方式安排产品顾问进一步沟通。
方案 B：第一版保存到最小 SQLite 表
优点：
留资闭环完整；
后续可以导出给销售；
方便验收转化效果。
缺点：
需要新增表和接口；
略微增加开发量。
建议表：
lead_captures
- id
- session_id
- contact_type
- contact_value
- visitor_type
- interest_summary
- created_at
我的建议：即使第一版不做 CRM，也最好保存到最小 SQLite 表。
9.5 参考来源确认
请确认：
访客模式不展示参考来源。
后续销售登录模式再展示参考来源。
10. 风险与注意事项
10.1 不保存联系方式的风险
如果第一版完全不保存联系方式，产品会出现问题：
AI 引导用户留下电话/微信
但系统没有地方承接
这会导致销售无法跟进。
因此建议至少新增最小线索记录。

10.2 Prompt 过度销售风险
AI 不能每轮都强行要电话，否则体验会变差。
建议规则：

用户表达购买/试用/演示/价格/合作时重点引导；
普通产品问答时只轻量追问；
无互动提醒每会话最多一次。
10.3 知识库不足风险
如果语雀知识库内容不足，AI 会难以准确讲解产品。
建议补充知识库文档：

平台一句话介绍；
核心功能；
适用人群；
老师使用场景；
学生使用场景；
家长关注点；
机构/学校价值；
使用案例；
试用方式；
购买/合作流程；
常见问题；
不能承诺的边界。
10.4 访客模式泄露内部资料风险
访客模式不应展示内部来源或内部文档标题。
当前系统有 sources 字段，第一版需要确保前端隐藏，生成内容也不要包含“参考来源”。 

11. 推荐开发顺序
我建议按以下顺序实施：
1. 人工确认 PRD 和关键决策
2. 前端欢迎语 + 页面文案 + 快捷问题改造
3. 访客模式隐藏来源
4. 后端访客销售 prompt
5. 购买/试用/联系方式识别
6. 长时间无互动提醒
7. 自动化测试
8. 手动验收
9. 根据验收反馈微调话术和策略
