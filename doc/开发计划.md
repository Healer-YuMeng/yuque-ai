# 开发计划（新人向 · 功能与准确性优先）

> **读者**：负责继续实现本仓库 RAG 与问答链路的工程师。  
> **协作文档**：[AGENTS.md](../AGENTS.md)、[README.md](../README.md)。  
> **规划依据**：合并「企业级 RAG MVP 薄全栈」与「Skill 路由 MVP」两条规划线的**目标与约束**（原草案见本地 Cursor 计划：`yuque-rag-mvp`、`yuque-skill-mvp`）。  
> **当前优先级**：**不**以向客户/公司演示为第一目标；优先保证 **最小功能闭环可用、回答有据、行为可预期、可测试可回归**。

---

## 1. 文档目的

把「下一步开发重点」写成**可执行、可验收**的清单，对齐两条规划里的核心主张：

- **RAG MVP 线**：语雀 → 切片 → 向量索引（可选）→ 检索 →（低置信/空命中）MCP fallback → 生成带 `sources`；配置集中、异步外呼、阈值显式。
- **Skill 线**：检索始终基于**用户原始问题**（`retrieval_question`），生成侧可注入 skill 指令（`generation_question`）；`stale-detector` 等需专用检索上下文时不得污染通用向量检索语义。

---

## 2. 北极星（本阶段）

**业务**：业务维护语雀知识库，用户用自然语言提问，系统**主要依据语雀内容**作答。  
**技术本阶段**：同一套后端 + 前端能 **稳定跑通问答**；检索与生成边界清晰；**无依据时有明确行为**；关键路径有测试与日志，便于你改参数不翻车。

---

## 3. 当前基线（与规划对照）

仓库已具备（与 `yuque-rag-mvp` 目标大体一致）：

- `app/` 分层：API → `QAService` → `RAGPipeline` → `Retriever` / `Generator`；`YuqueLoader`、`VectorStore`、`YuqueMCPClient`、SQLite 元数据与问答日志。
- `POST /chat`、`POST /chat/stream`、索引/同步接口、健康与运行时模式查询。
- 前端：React + Vite，流式聊天；本地会话缓存（`localStorage`）。
- `app/rag/skill_router.py` 与 `QAService` / `pipeline` 中的 **retrieval_question / generation_question** 拆分思路已落地（与 `yuque-skill-mvp` 一致）。

**仍应持续投入的方向**（= 本文件「下一步重点」）：召回质量与阈值、空结果与降级、语雀正文清洗、Skill 全路径一致性、测试覆盖与可观测性、**基础**可用前端（来源与错误可读，属于可用性而非「演示包装」）。

---

## 4. 下一步开发重点总览

| 优先级 | 主题 | 说明 |
|--------|------|------|
| **P0** | RAG 主链路正确性与可预期 | 阈值、空命中、fallback 触发、生成提示词与「无上下文」行为一致；日志可复盘 |
| **P0** | 索引与语雀数据质量 | 建索引/同步可靠；正文与 Markdown/富文本清洗，减少噪声切片 |
| **P1** | Skill 与检索协同 | 全分支确认 `retrieval_question` 未被指令污染；`stale-detector` 等专用上下文路径有测试 |
| **P1** | 自动化测试与小型评测集 | 单元测试 + 固定问题集（命中 / 弱命中 / 无命中）人工或半自动记录 |
| **P2** | 基础可用前端 | 展示 `sources` 与 `fallback_used`、HTTP 错误可读；不追求演示级包装 |
| **P2** | 工程底色 | `make test`、前端 `lint/build`；构建脚本可移植（见 [前后端启动说明.md](前后端启动说明.md) 常见问题） |

## 5. P0：RAG 主链路 — 准确性与可预期

**目标**：同一问题多次请求，行为类型一致（向量命中 / 语雀降级 / MCP fallback）；低质量上下文不硬编答案。

**建议任务**

1. **梳理并文档化 fallback 条件**（代码与 README 对齐）：`Retriever` 中向量分数、`top_k`、空结果、`FORCE_MCP_FALLBACK` 等与 [app/core/config.py](../app/core/config.py) 的对应关系；在 [README.md](../README.md) 或本文件附录写清「何种配置下走哪条路径」。
2. **空上下文与低置信**：对照 [app/rag/generator.py](../app/rag/generator.py) 中系统提示与实际传入 `contexts`；确认 [app/rag/pipeline.py](../app/rag/pipeline.py) 在所有返回路径上 **sources** 与 **answer** 语义一致。
3. **超时与错误**：语雀 / LLM / MCP 超时与异常是否在 [app/data/yuque_loader.py](../app/data/yuque_loader.py)、生成器、MCP 客户端中统一向上抛出，并在 [app/api/chat_api.py](../app/api/chat_api.py) 映射为明确 HTTP 状态与 `detail`（便于前端与排障）。
4. **日志**：在 `QAService` / `Retriever` 关键分支打结构化日志（模式、是否 fallback、sources 数量、耗时），满足「出问题能复盘」即可。

**验收**：用固定 5～10 个内部问题（覆盖高命中、边界词、库外问题）各跑 3 次，行为类型与回答风格符合预期；`make test` 通过。

## 6. P0：索引与语雀 — 可用性

**目标**：业务更新语雀后，通过脚本或 API 能**可靠**重建/同步；索引内容尽量贴近「人类可读正文」。

**建议任务**

1. 走通 [scripts/build_index.py](../scripts/build_index.py) 与 `POST /sync/yuque` / `POST /index/rebuild`：失败时有明确错误信息（Token、scope、网络、限流）。
2. **正文清洗**：评估语雀 HTML/Markdown 对 [app/data/splitter.py](../app/data/splitter.py) 的影响；必要时在入链前增加轻量清洗（避免表格/代码块打碎语义导致召回飘）。
3. **元数据一致性**：`documents` / `chunks` 与 FAISS 索引写入顺序、失败回滚或「失败即报错」策略明确，避免半套索引。

**验收**：在测试知识库上完整跑一轮「清空 → 重建 → 问答」无静默失败；与 [AUTHORING_GUIDE.md](../AUTHORING_GUIDE.md) 配合至少验证一篇长文、一篇 FAQ 结构文的切片效果。

---

## 7. P1：Skill 与检索 — 不破坏主 RAG

**目标**（对齐 `yuque-skill-mvp`）：除 `stale-detector` 等明确需要专用上下文的 skill 外，**检索查询保持用户原话**；生成侧 skill 指令只影响 `generation_question`。

**建议任务**

1. 代码走查：`chat` / `chat_stream`、动态 `model`/`owner` 分支（若存在）是否**全部**传入正确的 `retrieval_question` 与 `generation_question`（[app/service/qa_service.py](../app/service/qa_service.py)、[app/rag/pipeline.py](../app/rag/pipeline.py)）。
2. [app/rag/retriever.py](../app/rag/retriever.py)：`skill_id == stale-detector` 时 `list_docs` 元信息上下文是否稳定；与其它 skill 组合无回归。
3. **测试**：在 [tests/](.) 中为每个 skill 至少保留「触发短语 → `debug` 中含 skill_id」类断言；`stale-detector` 对 `updated_at` 有断言或快照（与规划验收一致）。

**验收**：`pytest` 全绿；手动对 8 类触发语各问一次，确认检索未被指令文本污染（对比关闭 skill 时的命中文档集合是否一致，除 stale 专用路径外）。

---

## 8. P1：测试与小型评测

**目标**：改阈值、改 prompt、改切片时有安全网。

**建议任务**

1. 维持并扩展 [tests/test_retriever.py](../tests/test_retriever.py)、[tests/test_chat_api.py](../tests/test_chat_api.py)、splitter/pipeline 相关用例；新行为先写失败用例再实现（若你习惯 TDD）。
2. 在仓库内维护一份 **评测问题表**（可放在 `doc/` 下简单 Markdown 表格）：问题、期望路径（向量/MCP/直搜）、期望是否引用来源、备注；每次发版前人工跑一轮并打勾。

**验收**：CI 或本地 `make test` 为合并前提；评测表至少覆盖 5 条。

---

## 9. P2：基础可用前端（非演示向）

**目标**：开发与联调时**一眼看到**依据与是否 fallback；失败时**可读**，减少「只有 debug JSON」的摩擦。

**建议任务**

1. [frontend/src/App.tsx](../frontend/src/App.tsx)：消费 SSE `done` 中的 `sources`、`fallback_used`，在助手消息下展示结构化「参考来源」列表（标题、可选链接受 `EXPOSE_SOURCE_URLS` 控制）。
2. `fetch` 非 2xx 时解析 FastAPI `detail` 展示给用户。
3. 可选：折叠原始 `debug` JSON，默认展示摘要。

**验收**：不打开浏览器开发者工具也能判断「答据何来、是否走了补充检索」；错误信息可复述给同事。
