## 1. 背景与目标

当前项目已经具备以下基础能力：

1. 可以通过语雀 API 拉取文档内容。
2. 已完成从 SQLite 向 PostgreSQL 的迁移。
3. PostgreSQL 已具备 `pgvector` 能力，可承载后续向量检索。
4. 管理后台已经具备基础素材管理能力，支持视频元数据和场景文本维护。

但当前知识库链路仍存在明显限制：

1. 现有检索能力主要面向文本正文，尚未形成稳定的多模态知识入库链路。
2. 语雀文档包含文字、表格、图片、视频与目录层级，现有方案无法完整利用这些内容。
3. 管理员无法在后台主动管理“语雀知识库同步与向量重建”过程。
4. 现有重建接口更接近技术接口，不适合直接作为后台运营能力使用。

本期目标是将语雀知识库升级为一套可运营的多模态 RAG 知识底座：

1. 语雀文档可被结构化抽取。
2. 文本、表格、图片说明等可被切块并向量化。
3. 向量结果写入 PostgreSQL + pgvector。
4. 访客提问时优先从向量数据库召回相关知识。
5. 管理员可在后台发起语雀同步与向量更新。

---

## 2. 产品定位

本能力不是单纯增加一个“向量库”，而是建设一套完整的“语雀知识库管理与检索底座”。

它包含两层：

1. 原始知识层：负责保存语雀文档、目录、多媒体资源及解析结果。
2. 检索服务层：负责切块、向量化、向量召回与回答引用。

一句话定义：

`把语雀知识库升级为可同步、可解析、可向量检索、可后台管理的多模态 RAG 知识底座。`

---

## 3. 设计原则

### 3.1 原始内容优先

不采用“整篇 md 直接交给 LLM 重做全文识别”的重方案。

优先顺序应为：

1. 语雀正文直接解析。
2. 表格单独结构化转换。
3. 图片通过 OCR / 多模态模型补充理解。
4. 视频先保留元数据与摘要，后续再逐步增强。

### 3.2 分层存储

不把“原始文档”“切块结果”“向量结果”混在一起。

至少分为：

1. 文档层
2. 文档块层
3. 检索块层
4. 向量层
5. 同步任务层

### 3.3 增量更新优先

后台点击“更新知识库”时，优先采用增量同步，而不是默认全量重建。

### 3.4 可回退

若多模态解析失败，系统仍应保留纯文本链路，不影响基础问答。

## 4. 范围定义

### 4.1 本期要做

1. 接入语雀文档拉取与目录结构读取。
2. 将语雀文档标准化为中间结构。
3. 支持对正文、表格、图片说明进行切块。
4. 使用千问 Embedding 模型进行向量化。
5. 将向量写入 PostgreSQL + pgvector。
6. 访客问答时接入向量召回结果。
7. 在管理员后台增加“知识库管理”能力。
8. 管理员可点击发起语雀同步与向量更新。
9. 后台展示同步状态、同步结果与基础统计。

### 4.2 本期不做

1. 不做视频逐秒理解。
2. 不做复杂音频 ASR 全量接入。
3. 不做多管理员协同审批流。
4. 不做知识库权限分级。
5. 不做自动定时任务调度的复杂编排平台。

---

## 5. 整体链路

整体业务链路如下：

1. 管理员在后台点击“同步语雀知识库”。
2. 系统读取语雀目录与文档列表。
3. 系统识别新增、修改、删除的文档。
4. 系统拉取变更文档正文与媒体信息。
5. 系统将文档转为统一中间结构。
6. 系统生成文档块与检索块。
7. 系统调用千问 Embedding 模型生成向量。
8. 系统写入 PostgreSQL + pgvector。
9. 访客提问时，从向量数据库召回相关内容。
10. 召回结果再交给生成模型组织最终回答。

## 6. 语雀文档解析方案

### 6.1 输入来源

语雀知识库通过官方 API 提供以下内容：

1. 文档标题
2. 文档正文
3. 文档 URL
4. 文档更新时间
5. 目录层级关系
6. 文档内图片、视频、表格等内容

### 6.2 中间结构

每篇语雀文档在进入切块前，应先转成统一的中间结构，例如：

1. `doc_id`
2. `title`
3. `path`
4. `url`
5. `updated_at`
6. `content_blocks`
7. `images`
8. `videos`
9. `tables`

其中：

1. `path` 表示目录层级路径，如“平台介绍 / 智能招生 / 使用说明”。
2. `content_blocks` 表示正文中的段落、标题、列表等基础文本块。
3. `images` 保存图片资源及图注、OCR 文本、视觉摘要。
4. `videos` 保存视频资源及基础元数据、说明、字幕摘要。
5. `tables` 保存表格原始内容与结构化文本表达。

### 6.3 图片处理原则

图片分两类处理：

1. 含文字图片：走 OCR，提取文字内容。
2. 非文字型图片：保留图片资源，并生成图注级摘要。

图片不建议直接作为主检索单元入库，而应转成可被检索的描述文本。

### 6.4 表格处理原则

表格不能简单忽略。

应将表格转换为更适合检索的结构化文本，例如：

1. 表头
2. 每一行主要字段
3. 表格结论摘要

### 6.5 视频处理原则

本期视频只做“可被引用的知识元数据”，不做重视频理解。

本期建议保存：

1. 视频标题
2. 所属场景
3. 封面图或图注说明
4. 视频简介
5. 可选字幕摘要

---

## 7. 切块策略

### 7.1 切块目标

切块不是简单按固定字数截断，而是要保留文档结构与语义边界。

### 7.2 推荐切块规则

优先按以下边界进行切块：

1. 一级/二级/三级标题
2. 段落语义块
3. 表格块
4. 图片说明块
5. 视频说明块

### 7.3 每个 Chunk 的必要元数据

每个 chunk 至少应保存：

1. `chunk_id`
2. `doc_id`
3. `title`
4. `path`
5. `section_heading`
6. `block_type`
7. `text`
8. `image_refs`
9. `video_refs`
10. `updated_at`

### 7.4 检索友好要求

切块后的文本应满足：

1. 单块语义完整
2. 不跨太多主题
3. 尽量保留上下级标题信息
4. 可单独被模型理解

---

## 8. 向量化与数据库方案

### 8.1 向量模型

本期采用千问 Embedding 模型进行向量化。

### 8.2 向量数据库

本期统一采用：

1. PostgreSQL
2. pgvector

### 8.3 数据库存储原则

数据库中不仅要存向量，也要存原始 chunk 文本和业务元数据。

原因：

1. 便于检索后直接回填上下文。
2. 便于后续更换 embedding 模型重新建索引。
3. 便于后台查看知识块内容。

### 8.4 推荐表结构

建议逻辑上至少包含以下几类表：

1. `documents`
   - 文档级信息
2. `document_blocks`
   - 原始解析块，区分 paragraph / table / image / video
3. `chunks`
   - 最终用于检索的切块结果
4. `chunk_embeddings`
   - pgvector 向量
5. `assets`
   - 图片/视频资源及说明
6. `doc_hierarchy`
   - 目录层级关系
7. `sync_jobs`
   - 同步任务与执行结果

---

## 9. 问答检索链路

访客提问后的回答链路如下：

1. 接收用户问题
2. 对问题做基础改写或意图识别
3. 从 PostgreSQL + pgvector 召回相关 chunks
4. 按需要补充图片说明、表格摘要、视频摘要
5. 将召回内容传给生成模型
6. 输出最终答案

回答目标不是“把所有原文直接拼上”，而是：

1. 优先命中最相关内容
2. 尽量保留目录上下文
3. 必要时引用表格与图片说明
4. 支持后续扩展到多模态生成模型

## 10. 管理后台需求

### 10.1 模块名称

管理后台新增或升级一级模块：

1. 知识库管理

该模块不仅管理本地视频素材，也负责管理语雀知识库同步与向量更新。

### 10.2 页面目标

让管理员能够理解并控制“语雀内容是否已同步、是否已完成向量化、当前知识库是否为最新版本”。

### 10.3 页面核心能力

本期页面至少包含以下能力：

1. 查看最近一次同步时间
2. 查看当前同步状态
3. 查看知识库文档总数
4. 查看 chunk 总数
5. 查看向量总数
6. 查看本次新增/更新/删除文档数
7. 手动点击“同步语雀”
8. 手动点击“重建向量”
9. 查看失败原因或执行日志

### 10.4 推荐按钮设计

建议至少保留两个操作：

1. `同步语雀`
   - 拉取语雀最新文档与目录
   - 识别新增、修改、删除
2. `重建向量`
   - 对已有解析结果重新切块或重新 embedding

若本期为简化实现，也可先合并为一个按钮：

1. `更新知识库`

含义为：

1. 拉取最新语雀内容
2. 重新解析变更文档
3. 重新生成对应向量

### 10.5 后台状态字段

页面应展示以下状态：

1. 任务状态：未开始 / 进行中 / 成功 / 失败
2. 开始时间
3. 完成时间
4. 总耗时
5. 成功文档数
6. 失败文档数
7. 失败原因摘要

## 11. 同步策略

### 11.1 两种模式

系统应支持两种同步模式：

1. 全量重建
2. 增量同步

### 11.2 推荐默认策略

默认推荐使用增量同步。

增量同步流程：

1. 拉取语雀文档列表与 `updated_at`
2. 对比本地文档版本
3. 仅处理新增或更新的文档
4. 标记已删除文档
5. 只重建受影响的 chunks 和 vectors

### 11.3 全量重建的使用场景

以下场景可使用全量重建：

1. 首次初始化知识库
2. 切块规则发生重大变化
3. Embedding 模型切换
4. 数据异常后整体校正

---

## 12. 非功能要求

### 12.1 稳定性

1. 单篇文档解析失败不应阻塞整批任务。
2. 多模态解析失败时，可退化为纯文本入库。
3. 同步失败后应保留上一次可用索引。

### 12.2 性能

1. 后台同步应采用异步任务，不阻塞管理员页面。
2. 向量更新过程应支持批量处理。
3. 文档量增长后，应优先走增量更新。

### 12.3 可观测性

应记录：

1. 每次同步任务日志
2. 每次解析失败原因
3. 每次 embedding 批次状态
4. 文档、chunk、向量数量变化

### 12.4 可维护性

后续若更换模型或切块策略，不应要求重新设计整套数据库结构。

## 13. 本期阶段建议

### Phase 1：先跑通文本向量化

目标：

1. 语雀正文抽取
2. 标题层级保留
3. 文本切块
4. 千问 embedding
5. PostgreSQL + pgvector 存储
6. 后台可手动点击更新

### Phase 2：补齐表格与图片说明

目标：

1. 表格结构化
2. 图片 OCR / 视觉摘要
3. 进入统一切块逻辑

### Phase 3：补齐视频摘要与高级后台能力

目标：

1. 视频元数据整理
2. 可选字幕/关键帧摘要
3. 后台任务状态、日志、统计完善

---

## 14. 成功标准

本期完成后，应达到以下结果：

1. 管理员可以在后台手动触发语雀知识库更新。
2. 语雀最新内容可以重新进入向量库。
3. 新增或修改文档可在更新后被问答命中。
4. 文本、表格、图片说明可以进入统一检索链路。
5. 数据库中能清晰区分原始文档、切块结果、向量结果和同步任务。

## 15. 一句话总结

本期需求的核心，不是简单“把语雀文档存到向量库”，而是建设一套：

`可同步、可解析、可增量更新、可后台管理的语雀多模态知识库 RAG 底座。`
