# 多模态协同解析实施计划（DeepSeek + 千问）

## 1. 背景与目标

当前销售主链已具备：

- 语雀 MCP 检索与取文（`yuque_search` / `yuque_get_doc`）
- V4 单次生成与运行追踪（`debug.turn_trace`）
- 前端图文/视频结果渲染

但现阶段主要是从文档正文里提取链接并展示，尚未对图片像素内容、视频画面内容做稳定语义理解。

本计划目标是把链路升级为：**文本 + 图片 + 视频并行解析，最终单次汇总输出**，并保持可灰度、可回退、可控成本。

---

## 2. 范围定义

### 2.1 本期要做

1. 在 V4 中引入多模态解析编排层（不改 V1 主链）。
2. 同时支持三路证据：
   - 文本证据（语雀正文）
   - 图片证据（图片 URL -> 视觉模型）
   - 视频证据（优先字幕；无字幕时抽帧 -> 视觉模型）
3. 统一证据结构并做一次汇总生成（默认 DeepSeek）。
4. 在 `turn_trace` 中补充多模态调用追踪（模型、耗时、输入规模、结果状态）。
5. 增加开关，支持快速关闭多模态能力。

### 2.2 本期不做

1. 不做完整视频长内容逐秒理解（成本过高）。
2. 不做音频 ASR 全量平台接入（先保留接口位）。
3. 不替换现有 MCP 协议。

---

## 3. 目标架构

```mermaid
flowchart TB
    Q[用户问题] --> RET[语雀 MCP 检索/取文]
    RET --> TXT[文本解析器]
    RET --> IMG[图片解析器(千问视觉)]
    RET --> VID[视频解析器(字幕/抽帧+视觉)]
    TXT --> EVI[证据归一化]
    IMG --> EVI
    VID --> EVI
    EVI --> SUM[汇总生成器(DeepSeek)]
    SUM --> RESP[前端回答+媒体]
    EVI --> TRACE[turn_trace 多模态追踪]
```

核心原则：

- **并行解析**：文本/图片/视频独立执行，降低总时延。
- **单次汇总**：最终只做一次对外回答生成。
- **证据优先**：回答必须标注依据，避免凭空推断。

---

## 4. 模型分工建议

1. 文本模型：DeepSeek（现有）。
2. 图片模型：Qwen VL（阿里千问视觉）。
3. 视频模型：
   - 优先方案：抽关键帧后走图片模型
   - 可选方案：直接视频模型（若预算允许）
4. 汇总模型：DeepSeek（先复用现有能力）。

---

## 5. 分阶段实施

## Phase 0（准备）

目标：不改主流程，仅补配置和接口定义。

交付：

1. 新增配置项（建议）：
   - `MM_ENABLED`
   - `MM_IMAGE_ENABLED`
   - `MM_VIDEO_ENABLED`
   - `MM_MAX_IMAGES_PER_TURN`
   - `MM_MAX_VIDEOS_PER_TURN`
   - `MM_MAX_VIDEO_FRAMES`
   - `MM_TIMEOUT_MS`
   - `QWEN_API_KEY` / `QWEN_BASE_URL` / `QWEN_MODEL_IMAGE` / `QWEN_MODEL_VIDEO`
2. 定义统一结果结构（`evidence_items[]`）。
3. 约定错误码与降级策略。

验收：

- 开关关闭时行为与当前一致。
- 配置缺失不影响现网主链。

## Phase 1（图片解析）

目标：实现“文本 + 图片”双通道。

交付：

1. 新增图片解析模块（示例）：
   - `app/service/mm_image_parser.py`
2. 从已提取图片 URL 中筛选 TopN（按标题、上下文匹配度）。
3. 调用千问视觉获取结构化图片理解结果。
4. 接入证据归一层，并让汇总 prompt 使用图片证据。
5. `turn_trace` 增加 `multimodal.image` 记录：
   - 模型名
   - 输入图片数量
   - 成功/失败数量
   - 总耗时

验收：

- 指定含截图文档时，回答能引用图片中的关键步骤/元素。
- 图片模型失败时自动降级为文本回答。

## Phase 2（视频解析）

目标：在图片能力稳定后引入视频理解。

交付：

1. 新增视频解析模块（示例）：
   - `app/service/mm_video_parser.py`
2. 视频策略：
   - 有字幕：优先字幕摘要
   - 无字幕：抽关键帧（如 3-8 帧）送视觉模型
3. 产出统一 `video_evidence` 结构。
4. `turn_trace` 增加 `multimodal.video` 记录：
   - 视频数
   - 抽帧数
   - 解析耗时
   - 降级路径

验收：

- 用户问“视频里怎么操作”时，可给出关键步骤总结。
- 视频解析超时不阻塞主回答（超时走降级）。

## Phase 3（汇总优化与面板）

目标：提升稳定性与可观测性。

交付：

1. 汇总器加入“证据等级”：
   - 高：文本明确证据
   - 中：图片/视频明确证据
   - 低：合理推断（需标注）
2. 开发者面板追加多模态追踪区块：
   - 图片模型调用
   - 视频模型调用
   - 证据数量与失败原因
3. 新增成本与时延指标日志。

验收：

- 面板可看见每轮多模态调用明细。
- 线上可统计成功率、P95 耗时、单轮成本。

## Phase 4（灰度与发布）

目标：小流量上线并可快速回退。

交付：

1. 灰度策略：按环境变量或用户分组开启。
2. 回退预案：`MM_ENABLED=false` 一键回退到纯文本链路。
3. 发布清单与监控阈值。

验收：

- 灰度期间无阻断错误。
- 回退后功能与当前版本一致。

## 7. 风险与应对

1. 成本风险：多模型并行导致费用上升。
   - 对策：限制图片/视频数量与帧数；设置超时与预算。
2. 时延风险：视频解析拖慢响应。
   - 对策：并行执行 + 超时降级 + 先回文本后补充（可选）。
3. 幻觉风险：视觉模型误读。
   - 对策：证据分级与“推断标注”。
4. 链接可用性风险：外链视频不可播放。
   - 对策：前端展示可点击原链，并标注“播放受源站策略影响”。

## 8. 测试计划

1. 单元测试：
   - 图片/视频 URL 提取
   - 抽帧策略
   - 证据归一化
   - 开关降级
2. 集成测试：
   - V4 流式返回包含多模态 trace
   - 多模态失败不影响主回答
3. 手工验收：
   - 图片场景问题（截图步骤问答）
   - 视频场景问题（操作流程问答）
   - 关闭开关后的回归行为

---

## 9. 执行优先级建议

1. 先落地 **Phase 1（图片）**，用最小改动拿到业务增益。
2. 再做 **Phase 2（视频）**，分“字幕优先 / 抽帧补充”两步走。
3. 最后完善 **Phase 3/4** 做线上稳定化与灰度。

---
